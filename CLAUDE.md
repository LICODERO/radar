# R.A.D.A.R.

Repo AI Discovery And Review: local tool that scans a directory of repositories, shows their AI setup
(CLAUDE.md, agents, skills, workflows, memory), computes coverage and gaps, and generates Claude Code / Codex CLI
commands to fill them. The MVP is read-only, except for a few writes the user confirms (a new agent file, the second brain; see Conventions).

## Stack

- `src/api/Radar.Scanner` – .NET class library: repo discovery, detectors, coverage, gaps, progress events (`ScanEvent`).
- `src/api/Radar.Server` – ASP.NET Core minimal API, SSE, JSON state files, static hosting of the Angular build. Loopback only.
  Vertical slices: `Features/<Name>/` (Session, Settings, Scans, Files, Gaps, Agents, Vault, Relations) each hold their endpoints (`<Name>Endpoints.cs`,
  a `Map<Name>()` extension called from `Program.cs`), request records and logic; `Infrastructure/` holds Security and Storage. Namespaces follow folders (`Radar.Server.Features.Scans`, `Radar.Server.Infrastructure.Storage`...).
- `src/tests/Radar.Scanner.Tests`, `src/tests/Radar.Server.Tests` – xUnit; fixtures are built in temp dirs (repos cannot be committed inside a repo).
- `src/web/` – Angular (standalone components, signals, zoneless, Vitest). UI lives here.
- Storage: JSON files behind `IScanStore` (SQLite only if scan history is added later).

## Commands

```bash
./run.sh                           # build UI if needed + start the server on http://127.0.0.1:5178 (Windows: ./run.ps1)
./dev.sh                           # dotnet watch + ng serve (http://localhost:4200, /api proxied)
dotnet build
dotnet test                        # scanner + server tests

# UI (from src/web/)
npm start                          # ng serve; add ?mock (or ?mock=150 / ?mock=400) to use sample data without the server
npm test -- --watch=false          # Vitest
npm run build
node scripts/gen-mock.mjs          # regenerate src/web/public/mock/*.json
```

State lives in the data dir (`~/Library/Application Support/RADAR`): `settings.json`, `scan-result.json`.
Override with `Radar__DataDir` (tests and manual experiments must never touch the real one).

## API (all under /api, loopback only)

`GET session` (token) · `GET/PUT settings` · `POST pick-folder` · `GET scan/latest` · `GET file?repo=&path=` (read-only preview) · `GET gaps` (commands/prompts, server is the single source) · `POST agents/generate` (draft) · `POST agents` (create; `visibility: private` also hides it) · `POST agents/copy` (copy an agent to repos that lack it; a plan unless `confirm`; `visibility` as for create) · `POST local-file` (private workflow index + AGENTS.md import in CLAUDE.local.md, optionally public workflows in CLAUDE.md; a plan unless `confirm`) · `POST items/generate` (draft a skill or workflow) · `POST items` (create it; `visibility` as for agents) · `POST skills/copy` (copy a whole skill folder to repos that lack it; same plan/confirm/visibility contract) · `POST visibility` (make an agent/skill/workflow private or public; a plan unless `confirm`) · `GET/POST relations` (flow rules between repos: read from the repos' files / write the whole set; a plan unless `confirm`) · `GET/POST/PUT vault` (second brain status / create / relink) · `GET/POST vault/skill` (status / install the bundled skill) · `POST vault/projects` (second brain for one repo; preview unless `confirm`; `allowAccess` also lets Claude read the vault without a prompt there) · `GET tools` (platform, shell, claude/codex on PATH) · `POST run` · `POST scans` · `GET scans/current` ·
`GET scans/{id}/events` (SSE: started, phase, repo-found, repo-scanned, completed, cancelled, error) · `DELETE scans/{id}`.
`run` opens iTerm2 or Terminal.app (macOS: iTerm2 when it is installed, force one with `Radar__Terminal=terminal|iterm|auto`) or PowerShell (Windows) in the repo and starts `claude`/`codex` with the gap prompt; the client sends only repo id + gap type + tool, the server builds the command (never accept command text from the client). The server finds the tool itself (PATH, the usual install folders and every nvm Node version, newest first) and the terminal runs it by that absolute path, because a new shell only has the nvm default on its PATH (`GET tools` reports it in `toolPaths`); the copyable commands keep the plain name. The session is interactive, the app itself writes nothing into repos.
`file` only serves paths the latest scan reported for that repo (CLAUDE.md, agents, skills, workflows), `.md` only, max 256 KB, never through a symlink leaving the repo.
Everything except `session`/`health` needs `X-Radar-Token` (or `?token=` for SSE); Host must be loopback; foreign Origins are rejected.

## Conventions

- Version: one place, `Directory.Build.props` (`<Version>`); the server returns it in `GET session` and the UI shows it in the bottom-right About line/dialog. Bump it there for a release.
- The project name is written **R.A.D.A.R.** with the trailing dot everywhere (UI, README, scripts, docs, messages). Identifiers and paths (`Radar.*`, the `RADAR` data folder) are unaffected.
- Talk to the user in Polish; code, identifiers, commit messages and README are in English.
- i18n: the UI is bilingual (PL/EN, switch in the header, choice kept in localStorage `radar.lang`, default from the browser language, Polish fallback).
  Every UI string lives in `src/web/src/app/i18n/pl.ts` (source, defines the keys) and `en.ts` (must match; a spec checks keys and `{placeholders}`);
  use `inject(I18n).t('key', { params })` (plurals: message object with `one/few/many/other`, pick with `n`), never hard-coded text in templates.
  The client sends `Accept-Language`; API error texts come from `src/api/Radar.Server/Infrastructure/Localization/Messages.cs` (`Msg` enum, PL default).
- Commit messages: a single sentence in past tense, no description body, no Co-Authored-By.
- Scanning is local and read-only. Nothing leaves the machine. No network calls at runtime (fonts are bundled).
- Never read secrets (`.env`, keys); only AI/markdown files.
- Any file access by path must be resolved and validated to be inside a detected repo (no symlink escapes).
- Cross-platform: macOS and Windows are supported (Linux: everything except opening a terminal). Windows code paths (PowerShell launcher, folder dialog, `run.ps1`) are covered by unit tests of the builders but were not run on a real Windows machine yet.
- Drafting an agent, skill or workflow from a description (`POST agents/generate`, `POST items/generate`; prompts in `Features/Items/ItemPrompt.cs`, a workflow draft also gets the repo's agent and skill names to refer to) runs `claude -p` with no tools, `--strict-mcp-config --setting-sources project`, in an empty temp dir, and sends only the description, the stack name and existing agent names. Measured on the real CLI: ~0.06 cent per call with these flags vs ~5 cents without. `POST agents` writes one new `.claude/agents/<name>.md` into a repo (`POST items` a new `.claude/skills/<name>/SKILL.md` or `.claude/workflows/<name>.md`), only after the user confirms, never overwriting; `POST agents/copy` does the same for an agent that other repos already have (source read through the scan's validated paths, validated like a draft, up to 100 repos, same `AgentWriter`).
- Server listens on `127.0.0.1` only. Writes into a repo are limited to confirmed ones: a new `.claude/agents/<name>.md`, the RADAR block in `CLAUDE.local.md` (second brain), the RADAR block in `.git/info/exclude` (private list) and, when a tracked file is made private, `git rm --cached` on it (index only, the file stays on disk). RADAR never commits. `radar uninstall` (`Features/Uninstall/`, runs instead of the server; a listing unless `--confirm`) deletes the installed program folder, the `radar` link (Windows: the user PATH entry, the folder goes through a helper after exit) and with `--data`/`--skill` the app's data dir and the untouched bundled skill; it refuses a folder without `wwwroot` or inside a git repo and never touches repos, the vault or shell profiles. Everything else in repos is read-only (plus the app's own settings/cache).
- Second brain (`Features/Vault/`): a vault folder outside every repo (never inside a git repo; the check stops at the home dir), holding `.radar-vault.json` (marker, trusted only while present), `_indexMain.md` (project list between `radar:projects` markers + how to use the vault) and one folder per project (`raw/` read-only sources, `memory/` wiki, `outputs/`, `_index.md`). The path is `VaultPath` in `settings.json`; `GET vault` reports `none` / `ok` / `missing` (folder moved), and `PUT vault` relinks a moved folder (RADAR never moves files). `POST vault` needs an empty or new folder. `POST vault/projects` without `confirm` only returns a plan; with it, it creates the project folder (never overwriting) and upserts a block between `<!-- radar:second-brain -->` markers in the repo's `CLAUDE.local.md` (damaged markers, a link leading out of the repo, or a name clash refuse the write). The vault and CLAUDE.local.md texts are templates embedded in the server (`Features/Vault/Templates/`); the client never supplies them. RADAR does not read the vault content and no longer looks for `OUTPUTS.md` in repos. With `allowAccess` (on by default in the UI) `VaultAccess` adds the vault folder to `permissions.additionalDirectories` of the repo's `.claude/settings.local.json` (read access without a prompt; writes still follow the usual permissions; the entry only takes effect once the user trusts the folder). Claude Code only keeps that file out of git when it creates the file itself, so a file made here first goes through `PrivateFileGuard` (git already ignores it, or its line goes into RADAR's `info/exclude` block; refused when git cannot tell, when the file is tracked or the block is damaged). Everything else in the JSON is kept; a file that is not an object, has `permissions` of another shape or exceeds 1 MB blocks the whole enabling before anything is written. The project dialog also shows the state of the global `radar-second-brain` skill and installs it on request (same endpoint as the vault dialog).
- Bundled skill `radar-second-brain` (`SecondBrainSkill`): installed on request into `<CLAUDE_CONFIG_DIR or ~/.claude>/skills/radar-second-brain/SKILL.md` with a marker line (version + hash of the text above it). It never overwrites: a skill that is linked (also `skills/` itself), foreign or edited by hand is left alone; only an untouched older copy is updated, and only with `update: true`. Tests point `Radar:ClaudeDir` at a temp dir, so they never touch the real `~/.claude` (like `Radar__DataDir`).
- Layout: fixed 1440x900 stage scaled proportionally (`src/web/src/app/core/fit-scale.ts`, minimum scale 0.85, smaller windows scroll); use `fs(px)` from
  `src/web/src/styles/_tokens.scss` for every font size so fonts stay within 0.85x-1.2x. `fs()` also lifts the small design sizes (9-13 px) towards 14 px, because they were unreadable on a laptop; layouts with fixed row heights (repo and workflow lists, the selected-repo card) are sized for that, so check them when you change a font size. The left and right panels are both 720px tall (y=104 to 824): the workflow pager is pinned to the bottom of the left one and the actions to the bottom of the right one, so the two end on the same line; keep the heights equal.
- Palette: lime `#c6ff3d` (agents), violet `#a99bff` (skills), white `#e6e9f2` (repos), cyan `#4dd6ff` (workflows),
  magenta `#ff4fa3` (gaps), amber `#ffb84d` (memory). Repo colour by coverage: >=70 white, 40-69 amber, <40 magenta.
- Orbit geometry is pure functions in `src/web/src/app/orbit/` with unit tests; keep DOM code thin.
- Respect `prefers-reduced-motion`.

## Domain

- Repo = directory with `.git` under the scan path (recursive, default depth 4, skip `node_modules`, `bin`, `obj`, `.git`, `dist`...).
- Detected per repo: `CLAUDE.md`, `.claude/agents/*.md`, `.claude/skills/*/SKILL.md`, `.claude/workflows/*.md`.
- Workflow = per-project procedure for agents (how to code an API, check UI, commit...). Repo-scoped for now: it only relates to the agents/skills of the repo it lives in (orchestrator-level workflows are a later stage). Frontmatter: `name`,
  `description`, `when`, optional `agents` and `skills` (names of the agents/skills the procedure uses; picking a workflow in the UI lights them up). Same `name` across repos aggregates into one node (W1...).
- Coverage: CLAUDE.md 40 + agents(>=1) 30 + skills(>=1) 30.
- Gaps: `no-claude-md` (counted in the KPI), `no-agents`, `no-skills`, `workflow-not-linked`, `weak-files` (a file scores below 70, see Quality).
- Quality (`Quality.cs`, schema 2): coverage only says a file exists, quality says whether it is worth anything. Deterministic heuristics per file (CLAUDE.md: thin, too long, no commands, no headings, placeholders, `@`/link/`.claude/` references to files that do not exist, stale; agents: frontmatter, name, description length, tools, thin prompt, duplicate names; skills: frontmatter, description, thin body). A finding is `{ path, code, severity, detail }`; the code is turned into text by the UI (`quality.<code>` in `pl.ts`/`en.ts`) and by `QualityText` for the prompts, so a new code needs both. A file starts at 100 and loses 35/15/5 per error/warning/info; the repo score is the average of its files and does not hide one broken file (the gap looks at single files). Staleness = CLAUDE.md older than the repo's last git write (`.git/logs/HEAD`) by 180+ days; it only reads file times.
- Shared copies (`SharedItems.cs`): agents/skills with the same name in 2+ repos, grouped by content hash (`AgentInfo.Hash`/`SkillInfo.Hash`, line endings ignored); several hashes = drifted. `Missing` lists repos of the same stack that lack it. Skills are copied as whole folders (`Features/Skills/`: `SkillBundleReader` takes regular files only, max 50 files and 1 MB; symlinks and binary files outside `scripts/` are skipped and listed in the plan; the executable bit survives; a half-written folder is removed again).
- Coverage after a scan: the client remembers the average coverage before a scan the user starts and, when it completes on the same directory, shows `insights/coverage-toast` (rose / fell / unchanged, 8 s). Nothing is stored for it.
- Visibility (`GitVisibility.cs`, `GitProcess.cs`): every agent, skill and workflow carries `visibility` from git: `public` (tracked), `private` (untracked and ignored), `untracked` (neither, so it shows in git changes), `unknown` (git could not tell: no git, fake `.git` in fixtures). Two git calls per repo (`ls-files`, `check-ignore --stdin`), only for repos that have such files; a skill counts as public when any file in its folder is tracked. "Private" is kept in a RADAR block of the repo's `.git/info/exclude` (never `.gitignore`: it is not committed, so nobody sees what is kept private; `Features/Visibility/GitExclude.cs` owns the block between `# >>> radar:private >>>` markers and finds the file with `git rev-parse --git-path`, so worktrees and submodules work). The UI shows it as `app-visibility-tag` (hidden for `unknown`). `POST visibility` plans (nothing written) or, with `confirm`, edits the block and for a tracked item also runs `git rm --cached` (rolled back when git refuses; making an item public is rolled back when another rule such as a `.gitignore` pattern still hides it, and refused when the item is hidden by a line RADAR did not write). The UI opens it from the tag in the file pane (`visibility/visibility-dialog`). New files default to private in the UI (`app-visibility-picker`): `POST agents` and `agents/copy` with `visibility: private` first check that the file can be hidden and create nothing when it cannot (`cannot-hide`); an omitted `visibility` leaves the file as git sees it.
- Name conflicts (`NameConflicts.cs`, `RepoInfo.NameConflicts`, UI `conflicts/conflict-dialog`): the same name (case-insensitive) of an agent, skill or workflow used by a public file and a private/untracked one in one repo; items of unknown visibility and same-visibility duplicates (agents have `agent-duplicate-name` for those) are ignored. Claude sees both and may take the wrong one, and git refuses to pull once the shared file reaches the local file's path. The UI marks it with an amber warning button in the repo card header and in the file pane; the dialog asks which file stays and shows the command that removes the others (`git rm` for a shared one, a plain delete for a local one; skills go as whole folders; `core/conflict.ts`), to copy. RADAR never deletes anything for this.
- Local instructions (`Features/LocalFile/`, UI `local/local-file-dialog`, button "INSTRUKCJE LOKALNE" next to "OPEN CLAUDE.md"): Claude finds agents and skills on its own, but a workflow only exists for it when a file it always reads says so. `LocalFileService` keeps marked blocks (`<!-- radar:workflows -->`, `<!-- radar:agents-md -->`; texts in `LocalBlocks`, English because Claude reads them, short because both files are loaded every session): the index of private/untracked workflows and the `@AGENTS.md` import (a CLAUDE.local.md, like a CLAUDE.md, makes Claude stop reading an AGENTS.md on its own, so the import is added whenever the repo has an AGENTS.md and no CLAUDE.md; the second-brain flow adds it too) go to CLAUDE.local.md, the public workflows CLAUDE.md does not mention yet go to a block in CLAUDE.md only when the user ticks it (a tracked file: a commit is needed). Before writing CLAUDE.local.md the service makes sure git ignores it (RADAR's `info/exclude` block); it refuses when git cannot tell, when the file is already tracked, or when markers are damaged, and restores everything if a write fails. A workflow named in CLAUDE.local.md counts as linked for the `workflow-not-linked` gap. The second-brain block also tells Claude to use the `radar-second-brain` skill: the repo block stays a short pointer, the details live in the vault and the skill.
- Flow between repos (`Features/Relations/`, UI `flow/flow-dialog` opened from the bottom-left "FLOW BETWEEN REPOS" button): a rule says `from` (the consumer) calls `to` (the provider) by `kind` (rest, graphql, grpc, events, db, files, other) with `auth` (none, api-key, oauth-client, bearer, basic, mtls, other), the **names** of the variables holding the secrets (`authEnv`, validated as identifiers, so a pasted value is refused; secrets are never stored or read), a `direction` (out: from sends to to, in: from receives, both; request/response kinds rest/graphql/grpc are always out, the call itself is the direction, and the file then has no `Data flow` line), a `contract` (no longer in the UI, kept when present) and `notes` (one line, no `<!--`/`-->`, backticks replaced), and a `visibility`. Repos are addressed by name (a name shared by two scanned repos blocks the rule), never by path, so rules can be committed. A rule lives in **both** repos: `.claude/relations.md` (public rules, committed) or `.claude/relations.local.md` (private rules, kept out of git through `PrivateFileGuard`), each holding a marked block `<!-- radar:relations -->` with readable text plus one JSON fence that RADAR reads back (`RelationsText`); there is no separate store, the graph is rebuilt from the files of the scan (a file only speaks for its own visibility). CLAUDE.md (public) or CLAUDE.local.md (private, with the AGENTS.md import when needed) gets a short `<!-- radar:relations-ref -->` pointer telling the agent to read the file before touching an API/event/auth/data shape that crosses a repo, to look at the named repo (sibling folder `../<name>`) through its agent, say what has to change there and **ask before editing it**. `POST relations` takes the whole desired set: it diffs against what the files hold, plans (or with `confirm` writes) every affected repo all-or-nothing (any block, damaged marker or tracked private file refuses the whole write; a failure restores every file), and removes blocks and emptied files RADAR created. A repo without CLAUDE.md gets the file and a `no-claude-md` note. The board has four dots per card (any two can be joined; the dragged-from repo is the caller, `swap` turns it around), zoom/pan, drag from the repo list and a repo search; the card positions and which dots a line uses are only kept in localStorage (`radar.flow.layout`, `radar.flow.ports`), the wizard is lazy-loaded (`@defer`) to stay under the bundle budget; Escape and the backdrop do not close the wizard while it holds unsaved rules (`flowDirty`).
- Copying an agent or a skill: from the file pane (right, "copy to another repo") to `insights/copy-agent-dialog`: it lists repos without an agent of that name (the source's stack first, nothing ticked), asks the server for a plan, writes on confirm. The shared-copies view (`insights/insights-dialog`, bottom-left button) is read-only.

## Stages

1. Skeleton + Orbit layout on mock data (done).
2. Scanner + JSON result + tests on fixtures (done).
3. Scan from the UI: SSE progress overlay, saved result, "last scan", folder picker (done).
4. Read-only markdown preview + command generator for gaps (done), plus URUCHOM: opens a terminal after an explicit confirmation. Prompts live in `src/api/Radar.Server/Features/Gaps/GapCommands.cs`; the UI formats commands per shell in `src/web/src/app/core/commands.ts`.
5. Distribution (GitHub Actions release binaries).
6. Second brain: vault logic, bundled skill and per-repo enabling on the server, and their UI in `src/web/src/app/vault/` (`vault-dialog`: intro / location / manage / relink + skill install, `project-dialog`: preview then confirm; opened from the right panel) are done; repo relations are done too (the flow wizard above); the second brain's own relations (export/import of a vault's relation map) are still open.

## Distribution

The repository is **public** (MIT). Releases, installers and the site all live here.

- Releases: push a tag `vX.Y.Z` (it must equal `<Version>` in `Directory.Build.props`, and `CHANGELOG.md` needs a `## X.Y.Z – date` section). `.github/workflows/release.yml` builds the UI once, then self-contained single-file binaries (`osx-arm64`, `osx-x64`, `win-x64`, `linux-x64`) with the UI in a `wwwroot` folder next to the executable, smoke-tests them and the install scripts (start from another directory, `/api/health`, the UI) and creates a **draft** release in this repo with the built-in `GITHUB_TOKEN` (no extra secrets). Publishing the draft is a manual step. Assets keep fixed names without a version so `releases/latest/download/<name>` links never change. A published copy resolves `wwwroot` from `AppContext.BaseDirectory` (see `Program.cs`), not from the working directory. A push to a `dryrun/**` branch runs the same builds without publishing anything.
- Install paths, all in the repo root: `AGENT_INSTALL.md` (the README and the site tell the user to paste one sentence to their coding agent, which reads it), `install.sh` (macOS/Linux), `install.ps1` (Windows) and `INSTALL.md` (every way, for people: agent, one command, by hand, from source). The scripts fetch the archive from the latest release, refuse a wrong SHA256, unpack into `~/.radar/app` (`%LOCALAPPDATA%\RADAR\app`) and need no admin rights; a file fetched from a terminal carries no quarantine/Mark-of-the-Web, which is why the unsigned app shows no OS warning that way (only manual browser downloads do). The release workflow runs the real scripts against a local copy of each archive (`RADAR_BASE_URL`) on every platform it can smoke-test. Where they are served from is `RAW` in `site/assets/config.js`.
- Claude Code plugin: the repo root is also a plugin marketplace (`.claude-plugin/marketplace.json`, name `radar`) listing one plugin, `plugins/radar` (skills `install`, `start`, `update`, `uninstall`, run as `/radar:<name>`). It holds no binary: the skills point at `AGENT_INSTALL.md` on `main` and at `radar uninstall`, so the install steps live in one place. `uninstall` has `disable-model-invocation` so Claude never runs it on its own. `plugin.json` has no `version` on purpose: users then follow the commit, and there is nothing to forget to bump (`claude plugin validate` warns about it). Check changes with `claude plugin validate .`, and test an install with a throwaway `CLAUDE_CONFIG_DIR` so the real settings are not touched. Claude reads the marketplace from the default branch, so it only reaches users after a merge to `main`.
- Third-party licences ship as `THIRD-PARTY-NOTICES.md` inside every archive; update it when `src/web/package.json` dependencies change. `SECURITY.md` states the safety rules the app keeps (and how to report a problem), `CONTRIBUTING.md` how to work on it; keep them true when those rules change.
- CI (`ci.yml`): Linux on every push, macOS and Windows on pull requests into main and on demand. Settings → Actions → General requires approval for runs from outside contributors.
- The one-page site lives in `site/` (see its README) and is published by `pages.yml` with GitHub Pages at `radar.licodero.pl` (`site/CNAME`). Binaries are not signed or notarized (no paid certificates): the docs tell people who download in a browser to run `xattr -dr com.apple.quarantine` (macOS) or to click through SmartScreen (Windows).
- `README.md` uses the images in `assets/` (logo, two screenshots). They come from the app run on a demo workspace, never on real repositories; regenerate them when the UI changes noticeably.

Requirements, mockup and the MVP spec live outside the repo (see `CLAUDE.local.md` if present).
